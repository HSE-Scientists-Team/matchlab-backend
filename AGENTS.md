# Работа с репозиторием MatchLab Backend

Это учебный Go-монорепозиторий с десятью сервисами: `gateway` (публичный HTTP API), `auth` (сеансы в Redis), `user` (учётные записи и подтверждение электронной почты в PostgreSQL) `mail` (синхронная отправка писем через SMTP) `media` (метаданные файлов в PostgreSQL и объекты в S3), `support` (жалобы), `project` (проекты, роли, команда и заявки), `search` (поисковый фасад к User/Project) `recommendation` (случайная выдача через Search) и `admin` (служебные аккаунты, сеансы и административный фасад). Каждый из десяти сервисов применяет весь общий SQL-набор PostgreSQL перед запуском API; параллельные старты сериализуются advisory-блокировкой. Контракты gRPC находятся в `api/proto`, описание публичного HTTP API и self-hosted Scalar — в `api/http`, реализации — в `internal`, точки входа, Dockerfile, примеры конфигурации и инструкции по запуску — в `cmd/<service>`. Пакет `pkg/healthcheck` предоставляет проверки работоспособности HTTP и gRPC. Актуальные имена сервисов, маршрутов, полей и команд сверяйте с кодом и README.

Локально проект запускается командой `docker compose up --build` из корня репозитория. Compose поднимает PostgreSQL, Redis и Mailpit; Gateway доступен на `http://localhost:8080`, письма — на `http://localhost:8025`. У PostgreSQL есть постоянный том, у Redis его нет: перезапуск Redis удаляет сеансы. Для прямого запуска Go-сервиса используйте его `config.example.yaml` и флаг `-config`. Файлы `config.compose.yaml` предназначены для Compose.

В рабочем окружении сервисы работают в собственном кластере k3s на виртуальных машинах одного хоста Proxmox. Исходный код, Dockerfile, миграции и примеры локального запуска находятся здесь. Манифесты k3s, ConfigMap, ссылки на Secret, хранилище, ingress и GitOps принадлежат отдельному инфраструктурному репозиторию; не добавляйте их сюда без явного требования. PostgreSQL хранит транзакционные данные, Redis — краткосрочные сеансы. Планируемые аналитические запросы используют отдельный ClickHouse; не предполагайте, что уже существующий сервис обращается к нему. Мониторинг ведётся через Zabbix.

## Границы сервисов

- Сохраняйте отдельные точки входа, конфигурации, API, миграции и владение данными сервисов. Общие пакеты добавляйте только для устойчивого общего кода; не импортируйте `internal` одного сервиса в другой.
- Межсервисные адреса задавайте в конфигурации через DNS-имена сервисов, без IP подов, ВМ или кластера. Для исходящих запросов задавайте тайм-ауты, передавайте `context.Context`, обрабатывайте недоступность зависимостей. Повторяйте только операции, безопасные для повтора.
- Публичный HTTP API обслуживает Gateway; внутренние gRPC-сервисы и базы данных не открывайте наружу без явного требования.

## Конфигурация и данные

- Несекретные настройки берутся из YAML (по умолчанию `/etc/app/config.yaml`), секреты — из переменных окружения. Проверяйте обязательные параметры при запуске, не записывайте секреты в журнал и не коммитьте реальные учётные данные, токены, kubeconfig или манифесты Secret.
- Поддерживайте безопасные `config.example.yaml` и документируйте обязательные переменные окружения. Локальные переопределения и файлы с секретами должны игнорироваться Git.
- Схемой PostgreSQL `users` владеет User; Mail не хранит письма в PostgreSQL. User проверяет активные правила `users.trusted_email_domain` перед отправкой письма и при подтверждении токена; Mail не обращается к этой таблице. Для изменений схемы используйте SQL-миграции Goose в `pkg/migrations` с явными шагами Up и Down; внимательно проверяйте удаление данных. Все сервисы используют общий migration runner с session advisory lock на том же PostgreSQL-соединении, которое выполняет SQL. Сохраняйте проверку истории и SQL-отпечатков; миграции должны быть транзакционными и совместимыми с уже работающими версиями.
- Redis используется Auth для сеансов. Изменения схемы ClickHouse отделяйте от миграций PostgreSQL. Тестовые данные создавайте отдельно от запуска сервиса и только для явно выбранного локального окружения.

## Разработка и проверка

Перед правкой изучите соответствующий сервис, его README, `go.mod` и более конкретные `AGENTS.md`, если они есть. Не придумывайте отсутствующие контракты. При изменении HTTP API Gateway обновляйте `api/http/openapi.yaml` и примеры. При изменении настроек обновляйте примеры и документацию. Форматируйте Go-код через `gofmt`, добавляйте содержательные тесты для нового поведения и запускайте `go test ./...` либо тесты затронутых пакетов. Интеграционные тесты с контейнерами запускаются с `-tags=integration`; не предполагается доступ к живому кластеру в CI. GitHub Actions проверяет тесты и покрытие; отдельный workflow_dispatch вручную собирает выбранные образы (включая Scalar api-docs), публикует их в GHCR и опционально создаёт PR с digest в matchlab-infra через INFRA_REPO_TOKEN. Сборка каждого образа описана в Dockerfile соответствующего сервиса; доставка в кластер относится к инфраструктурному репозиторию.

Project владеет схемой `projects`, а User — версионированной проекцией `users.project_context` для контактов и отзывов. Снимки передаются через transactional outbox и защищённый `PROJECT_SYNC_TOKEN`; старые source_revision не откатывают состояние. Search/Recommendation не читают чужие таблицы и не создают бизнес-таблиц. Внутренние методы модерации не публикуются в Gateway. Новые SQL добавляйте следующими версиями, опубликованные 00001–00006 не меняйте.

Admin владеет схемой `admin`, служебные аккаунты и сеансы независимы от User/Auth. Межсервисные административные RPC проверяют Ed25519 assertion с audience и коротким TTL; приватный ключ есть только у Admin. Не пересылайте привилегированные заголовки из HTTP. Admin не обращается к таблицам User/Support/Project напрямую. Публичные HTTP-ручки администрирования находятся только под `/api/v1/admin`, а прежние роли публичных профилей не дают доступ. Новые административные секции OpenAPI генерируются командой `go run ./scripts/api/admin-openapi.go --write`; перед push проверяйте `--check`.
