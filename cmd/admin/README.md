# Admin — KAN-35

Admin предоставляет backend административного интерфейса. Внешний HTTP доступен только через Gateway под `/api/v1/admin`; внутренний gRPC — `admin:8090`. Фронтенд в эту задачу не входит. Контракт HTTP со всеми схемами находится в `api/http/openapi.yaml`, gRPC — `api/proto/admin/v1/admin.proto`.

## Владение данными и права

Admin владеет схемой `admin`: служебные аккаунты, сеансы, ограничитель попыток входа и общий аудит. Публичная регистрация не создаёт сотрудников. Служебный email не обязан проходить правила регистрации User: аккаунт создаёт оператор/другой администратор. Роли в `users.user_account` не дают доступ к этому API. Пользовательские и служебные токены несовместимы.

| Возможность | moderator | administrator |
| --- | --- | --- |
| Жалобы: очереди, фильтры, назначение, закрытие/отклонение/возврат, заметки, вложения, история | да | да |
| Достижения: очереди и архив решений, просмотр доказательств, одобрение/возврат за доказательствами | да | да |
| Пользователи: поиск, детали, блокировка/разблокировка, история | да | да |
| Проекты: просмотр всех состояний, скрытие/восстановление, история | да | да |
| Домены: список и история | да | да |
| Домены: создание, изменение, активация/деактивация | нет | да |
| Сотрудники: создание, просмотр, изменение роли/статуса, сброс пароля, отзыв сеансов | нет | да |
| Собственный профиль, смена пароля, выход | да | да |
| Статистика и аудит модерации | да | да |

Admin обращается к User/Support/Project по gRPC и не читает их таблицы. Мутация и подробная история решения атомарны у владельца. Для межсервисной авторизации Admin подписывает Ed25519 assertion на 30 секунд с audience конкретного сервиса, ID, ролью и email сотрудника. Закрытый ключ доступен только Admin; User/Support/Project получают только открытый ключ. Они не обращаются обратно в Admin. Входящие HTTP-заголовки служебных полномочий не пересылаются Gateway. Служебная подпись не принимается как обычный пользовательский сеанс.

Сотрудник с тем же email не может рассматривать собственное пользовательское достижение. Отдельные email не позволяют установить, что это один физический человек; для такого контроля нужна отдельная проверяемая связь идентичностей.

## Вход и управление сотрудниками

- `POST /auth/login`: email + password, возвращает отдельный bearer token, срок и сотрудника.
- `GET /me`, `DELETE /sessions/current`, `PUT /me/password`.
- `GET/POST /staff`, `GET/PUT /staff/{id}`.
- `PUT /staff/{id}/password` (пароль, причина и expected_revision), `DELETE /staff/{id}/sessions`.

Пароли — bcrypt cost 12, 12–72 **байта**. Сеанс — 32 случайных байта, в PostgreSQL хранится только SHA-256-хеш. Срок — восемь часов без автоматического продления. Admin проверяет активность аккаунта и `session_version` в БД на каждом запросе; смена пароля, роли, статуса и принудительный отзыв сразу делают старые сеансы недействительными. После смены собственного пароля нужно войти заново. Нельзя понизить/отключить последнего активного администратора; конкурирующие изменения сериализуются. Служебные аккаунты отключаются, а не удаляются вместе с аудитом.

Пять неудачных попыток на нормализованный email за 15 минут дают `429`; неизвестный и неактивный аккаунт возвращают одинаковую ошибку. Бакет сохраняется между репликами/перезапусками. Одновременно выполняются не более четырёх проверок пароля на процесс; перегрузка возвращает `503`. Истёкшие сеансы и устаревшие throttle-записи очищаются фоновым worker. Он также переводит старые незавершённые межсервисные намерения в `unknown`.

Первый администратор создаётся только оператором, без HTTP-регистрации и без пароля по умолчанию. Запустите локальный PostgreSQL и задайте `POSTGRES_PASSWORD`, затем передайте пароль через `ADMIN_BOOTSTRAP_PASSWORD` и выполните:

```sh
go run ./cmd/admin-bootstrap -config cmd/admin/config.example.yaml -email admin@hse.ru
```

В Compose после сборки образа:

```sh
docker compose run --rm --no-deps -e ADMIN_BOOTSTRAP_PASSWORD --entrypoint /admin-bootstrap admin -config /etc/app/config.yaml -email admin@hse.ru
```

Обе команды применяют общие миграции. Повторный bootstrap при существующих сотрудниках отклоняется. Передавайте пароль из менеджера секретов/скрытого ввода, не аргументом команды. Дальнейших сотрудников создаёт вошедший администратор через `/staff`.

## Очереди, решения и пагинация

- `GET /tickets`: `status=open|resolved|declined|closed`, автор `user_id`, `assigned_admin_id`, `unassigned_only`, `target_user_id`, `target_project_id`, текст и интервал создания. Открытые жалобы сортируются от старых к новым, закрытые — по последнему закрытию от новых к старым.
- `GET /tickets/{id}`, `POST /tickets/{id}/actions`, `POST /tickets/{id}/notes`, `GET /tickets/{id}/history`.
- Действия жалобы: `assign`, `unassign`, `resolve`, `decline`, `reopen`. Закрытие/возврат требуют комментария. Назначить можно активного сотрудника; история содержит прежнего и нового исполнителя. Заметки внутренние и тоже увеличивают revision.
- `POST /tickets/{ticket_id}/attachments/{file_id}/download-url` проверяет принадлежность вложения конкретной жалобе и выдаёт временную ссылку через Media от имени автора. Произвольный файл получить нельзя.
- `GET /achievements`: состояния `unverified|pending_review|verified|needs_evidence`, вид `education|certificate|scientific|project`, владелец, текст и даты. Ожидающие решения сортируются FIFO, остальные — по недавнему обновлению.
- `GET /achievements/{id}`, `POST /achievements/{id}/decision`, `GET /achievements/{id}/history`, `POST /achievements/{id}/evidence/download-url`.
- Решение `approve=true` даёт `verified`, `approve=false` — `needs_evidence`, требует комментария и допускает повторную подачу. История сохраняет проверенную редакцию и file ID. Если файл уже удалён в Media, скачивание вернёт ошибку; новая политика удержания/неизменяемого хранения вложений здесь не вводится.
- `GET /users`, `GET /users/{id}`, `PUT /users/{id}/status`, `GET /users/{id}/history`: разрешены `active` и `blocked`, удалённый аккаунт таким способом не восстанавливается. Блокировка закрывает защищённые действия даже по старому пользовательскому токену; анонимные возможности не требуют регистрации. Разблокировка вновь разрешает ещё действующие пользовательские сеансы.
- `GET/POST /email-domains`, `PUT /email-domains/{id}`, `GET /email-domains/{id}/history`. Поддерживаются нормализованные ASCII/Punycode домены и `*.example.org`, без URL/email. Деактивация запрещает новую регистрацию и подтверждение ожидающей ссылки, но не блокирует существующих пользователей. Правила не удаляются вместе с историей.
- `GET /projects`, `GET /projects/{id}`, `PUT /projects/{id}/moderation`, `GET /projects/{id}/history`. Доступны все состояния проекта, фильтры `text`, `status`, `hidden_only`. Скрытие независимо от жизненного цикла.

Списки и истории используют `limit=1..100` (по умолчанию 20), `offset=0..10000`, стабильный порядок и `total`, даже если выбранная страница пуста. Неизвестные/неподдерживаемые фильтры отклоняются. Даты — Unix seconds UTC, верхняя граница исключительная. В HTTP int64 ответа кодируются строками согласно ProtoJSON. Управляющие boolean поля нужно явно передавать даже при `false`.

Мутации сущностей требуют `expected_revision`; устаревшая редакция даёт `409`, а не перезаписывает решение коллеги. Сброс сеансов — отдельная безопасная для повторения операция. Закрытие жалобы не блокирует человека и не скрывает проект автоматически: это отдельные решения с причинами и историей.

## Аудит и статистика

`GET /audit`: фильтры сотрудник, действие, результат (`started|succeeded|failed|unknown`), текст и время, пагинация. Общий аудит записывает намерение до gRPC-мутации и результат после неё. Сбой ответа не означает откат: `unknown`/незавершённая запись требуют сначала проверить состояние и историю у владельца. При недоступности Admin DB мутация не отправляется. При сбое записи итогового результата авторитетная история остаётся у владельца. В аудит не пишутся пароли, токены, ключи, URL скачивания и полные тела запросов. Чтение приватных доказательств тоже аудируется.

`GET /statistics?from_unix=...&to_unix=...` возвращает секции User, Support, Project и служебной активности: текущие распределения статусов, доменов и видов достижений, назначения открытых жалоб, видимость проектов; дневные регистрации, подачи/решения, жалобы/закрытия, проекты и входы. Диапазон по умолчанию — последние 30 дней, максимум 366 дней. Дневные даты — UTC; дни без событий могут отсутствовать. Общие счётчики — текущее состояние, дневные — активность в интервале. Закрытия/решения считают события, включая повторное рассмотрение.

Каждый владелец читает статистику в своём repeatable-read snapshot. Единого распределённого снимка нет. Недоступность любого источника даёт ошибку, а не ложные нулевые показатели. Модератор не получает распределение служебных аккаунтов по ролям/статусам.

## Конфигурация и выпуск

Admin: YAML `grpc`, `peers.user/support/project`, `postgres`, `metrics`; секреты `POSTGRES_PASSWORD`, `ADMIN_SIGNING_KEY` (base64 Ed25519 seed, 32 bytes). User/Support/Project получают `ADMIN_PUBLIC_KEY` (base64 public key, 32 bytes). Если ключ проверки отсутствует, административные операции закрыты. Compose содержит **только известную тестовую** пару ключей для разработки, не пригодную для рабочего окружения.

Для новой пары создайте игнорируемую Git директорию и запустите:

```sh
mkdir -p .local
go run ./scripts/admin-keygen --private-file .local/admin-signing-key --public-file .local/admin-public-key
```

Генератор не печатает ключи и не перезаписывает файлы. Приватный seed сохраняется с правами 0600; задайте окружение из файлов через свой менеджер секретов. При ротации согласованно обновите открытый ключ владельцев и закрытый ключ Admin. Действующие служебные сеансы не подписываются этим ключом; он защищает только внутреннюю делегацию.

Gateway включает маршруты, когда задан `admin.host/port`; без этой секции остальные маршруты продолжают работать, а административных HTTP endpoints нет. Сам Admin может работать при временной недоступности других сервисов; соответствующие операции вернут ошибку зависимости с тайм-аутом. Манифесты и секреты k3s принадлежат matchlab-infra и в этот PR не входят. Перед рабочим выпуском там нужны Deployment/Service Admin, ключи и адрес в Gateway; метрики Admin тоже нужно добавить в scrape allowlist.

Миграция `00007` добавляет схему и историю, не меняя опубликованные `00001–00006`. Все Go-сервисы запускают общий набор; перед выпуском нужно пересобрать весь набор, чтобы старые бинарники не отвергали новую историю при рестарте. Вручную собирается `service=admin` или `all`; Admin image также содержит `/admin-bootstrap`. Автоматическое добавление `ADMIN_IMAGE` в infra PR поддержано, но одно изменение digest не создаёт Deployment.

Down сохраняет старые ссылки авторов, но отказывается удалять накопленный административный аудит/решения. Перед откатом оператор должен отдельно архивировать и обработать эти данные.

## Генерация и проверка

```sh
go run ./scripts/api/admin-openapi.go --write
go run ./scripts/api/admin-openapi.go --check
go test ./...
go test -race ./pkg/adminauth ./internal/admin ./internal/gateway/delivery/http
go test -tags=integration ./internal/admin ./internal/user/profile ./internal/project ./pkg/migrations
```

Административные секции OpenAPI генерируются из protobuf и `scripts/api/admin-routes.json`; соответствие HTTP-маршрутам проверяется тестом. Protobuf обновляется `protoc` с теми же флагами module/go_out/go-grpc_out, что и остальные контракты.
