# Chat — личные текстовые чаты

Chat владеет схемой PostgreSQL `chat`: таблицами `conversation` и `message`.
Контракт — `api/proto/chat/v1/chat.proto`, Go-код — `internal/gen/chat/v1`.
Только диалоги двух пользователей, без вложений, редактирования и удаления сообщений.
HTTP предоставляет Gateway, внутри используется `matchlab.chat.v1.ChatService` на порту 8091.

## API и доступ

Все пять RPC принимают Bearer-сеанс в gRPC metadata. Chat вызывает User.GetIdentity;
User проверяет сеанс, активность аккаунта и подтверждённую почту. ID автора из тела не принимается.
Исходящие RPC передают только authorization через `pkg/rpcmeta`, без административных полномочий.
Тайм-аут RPC — 10 секунд через `pkg/grpcapp`, вызова User — 3 секунды; короткий deadline сохраняется.

| HTTP | Путь | gRPC |
| --- | --- | --- |
| POST | /api/v1/chat/conversations | OpenConversation |
| GET | /api/v1/chat/conversations | ListConversations |
| GET | /api/v1/chat/conversations/{id}/messages | ListMessages |
| POST | /api/v1/chat/conversations/{id}/messages | SendMessage |
| PUT | /api/v1/chat/conversations/{id}/read | MarkRead |

OpenConversation принимает user_id собеседника. Создание возвращает 201, существующий диалог — 200.
Собеседник должен существовать и быть активным по User.GetProfile; чат с собой запрещён.
При открытии и новой отправке User.CheckInteraction проверяет блокировку в обе стороны.
История и отметки прочтения остаются доступны участникам после блокировки.
Проверка User и транзакция Chat не являются распределённой транзакцией: блокировка,
зафиксированная одновременно с отправкой после проверки, может не остановить эту отправку.
Отсутствующий и чужой диалог одинаково возвращают NotFound / HTTP 404.

## Данные и конкурентные запросы

Пара UUID хранится в порядке user_low_id < user_high_id, UNIQUE исключает дубли диалога.
Идентификаторы User хранятся без межсервисных FK. Сообщения связаны FK с диалогом.
Только один из двух участников может отправить сообщение; проверку выполняет Chat.

SendMessage принимает client_message_id и body. Текст — 1–10000 Unicode-символов,
не только пробелы, без NUL; сохраняется без обрезки пробелов и обработки разметки.
Фронт должен отображать его как текст, а не HTML.
client_message_id создаётся фронтом один раз для нового сообщения и сохраняется при повторах.
Повтор с тем же текстом возвращает прежнее сообщение (200), даже если затем появилась блокировка;
изменённый текст с тем же ID — AlreadyExists / 409. Новое сообщение — 201.

Отправка блокирует строку диалога, проверяет повтор, затем политику взаимодействия,
выдаёт следующий seq, вставляет сообщение и обновляет last_message_seq / last_message_at
одной транзакцией. Неудачная отправка не расходует номер. Операции с read используют ту же блокировку.
Транзакция кратковременно удерживается во время проверки User для новой отправки.

MarkRead принимает last_read_seq от 0 до последнего номера. Отметка обновляется через GREATEST:
старый запрос не откатывает прочтение. Чтение истории само по себе не отмечает сообщения прочитанными.
unread_count учитывает только входящие сообщения после отметки, собственные не учитываются.

## Пагинация и формат

Список диалогов: limit 1–100 (по умолчанию 20), cursor. Сортировка по
coalesce(last_message_at,created_at) DESC, id DESC, включая пустые диалоги.
next_cursor берётся из ответа, пустая строка означает конец. Курсор привязан к пользователю;
это живая выдача, новые сообщения могут менять порядок между запросами.

История: limit 1–100 (по умолчанию 50), before_seq > 0 либо after_seq >= 0.
Без фильтра возвращается последняя страница; before_seq подгружает более старые,
after_seq — ближайшие новые сообщения после номера. Границы исключительные.
Ответ всегда в порядке seq ASC и содержит has_more. Для polling используйте after_seq;
если has_more=true, продолжайте с номером последнего полученного сообщения.

HTTP-ответы используют ProtoJSON с именами snake_case, как другие новые фасады проекта:
int64 (seq, счётчики, Unix timestamps) представлены десятичными строками.
В теле PUT read last_read_seq передаётся JSON-числом, фильтры seq — query-параметрами.
У пустого диалога last_message и last_message_at_unix отсутствуют либо null.

Ошибки: 400 — поля/пагинация/read за пределами истории, 401 — сеанс,
403 — неактивный аккаунт/неподтверждённая почта/блокировка, 404 — диалог или собеседник,
409 — повтор ID с другим текстом, 500 — ошибка Chat, 503 — User недоступен, 504 — тайм-аут RPC.

## Запуск и проверки

`docker compose up --build` поднимает Chat только во внутренней сети: `chat:8091`.
Секрет POSTGRES_PASSWORD берётся из окружения; grpc, peers.user, postgres и metrics — из YAML.
Прямой запуск после старта PostgreSQL и User:

```powershell
$env:POSTGRES_PASSWORD = 'matchlab_local_only'
go run ./cmd/chat -config cmd/chat/config.example.yaml
```

При одновременном прямом запуске нескольких сервисов задавайте разные локальные metrics.address.
`pkg/grpcapp` применяет общий SQL-набор до API, регистрирует health и метрики,
ограничивает RPC и выполняет graceful shutdown. Миграция 00008 создаёт две таблицы;
Down удаляет всю историю Chat и не затрагивает данные других сервисов.

```sh
go test ./...
go test -tags=integration -count=1 -v ./internal/chat ./pkg/migrations
go run ./scripts/api/admin-openapi.go --check
```

Интеграционные тесты требуют Docker с Linux-контейнерами, сами создают PostgreSQL.
Проверяют конкурентное создание диалогов, повторы отправки, порядок сообщений,
атомарность при ошибке, монотонность прочтения, доступ и пагинацию.

Генерация (protoc 34.1, protoc-gen-go v1.36.12, protoc-gen-go-grpc v1.5.1):

```sh
protoc --proto_path=. --go_out=. --go_opt=module=github.com/HSE-Scientists-Team/matchlab-backend --go-grpc_out=. --go-grpc_opt=module=github.com/HSE-Scientists-Team/matchlab-backend api/proto/chat/v1/chat.proto
```
