# Migrator

Одноразовая джоба применяет SQL-миграции PostgreSQL через Goose и завершает работу. Она не обслуживает запросы. Успешный выход имеет код `0`; ошибка подключения или миграции — ненулевой код. В Docker Compose включён `restart: on-failure`, а User ждёт успешного завершения джобы.

Миграции хранятся в [`internal/migrator/migrations`](../../internal/migrator/migrations). Существующая история Goose остаётся в `users.goose_db_version`, поэтому базы, ранее мигрированные сервисом User, продолжают работу без повторного выполнения версии `00001`. Новые миграции добавляйте следующими номерами; изменение уже применённых файлов не обновляет действующую базу. Целевая DBML-модель — описание планируемой схемы, её нельзя применять как SQL-миграцию.

Для локального запуска вместе с сервисами используйте `docker compose up --build`. Повторный запуск джобы: `docker compose run --rm migrator`. Логи: `docker compose logs migrator`. Не запускайте два экземпляра мигратора для одной базы одновременно. Если миграция постоянно падает, Compose будет повторять попытки: исправьте причину, прежде чем запускать User.

Конфигурация читается из YAML (`-config`, по умолчанию `/etc/app/config.yaml`); пример — [`config.example.yaml`](config.example.yaml). Пароль задаётся только через `POSTGRES_PASSWORD`. Для независимой выкладки сервисов сначала применяйте совместимые миграции, затем обновляйте затронутые сервисы; удаление старых столбцов выполняйте после перехода всех потребителей.

Проверка: `go test ./internal/migrator/...`; интеграционный тест с PostgreSQL: `go test -tags=integration ./internal/migrator/migrations`.
