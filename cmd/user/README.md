# Сервис User

User владеет учётными записями, хешами паролей и подтверждением почты в PostgreSQL `users`. Email обязателен при регистрации, нормализуется в нижний регистр и служит идентификатором входа. Отдельного логина нет. Пароли хранятся как bcrypt-хеши.

## Регистрация и подтверждение

Регистрация сохраняет заявку и сразу отправляет письмо через Mail. Аккаунт и сеанс создаются только после подтверждения и последующего входа соответственно. Пока существует лишь заявка, вход возвращает ошибку неверных учётных данных (`401`).

- `registration_request` хранит нормализованный email, bcrypt-хеш пароля, SHA-256-хеш одноразового токена и срок действия 30 минут. У заявки нет `user_id` и связи с аккаунтом.
- Любая повторная регистрация того же email заменяет пароль, токен и срок заявки. Знать предыдущий пароль не требуется; старые ссылки перестают действовать. Поэтому чужая незавершённая заявка не мешает владельцу почты зарегистрироваться со своим паролем.
- Подтверждение актуального токена атомарно создаёт `user_account`, записывает подтверждение в `user_email` и удаляет заявку. В аккаунт переносится пароль именно подтверждённой заявки. Использовать токен повторно нельзя.
- `user_account.email` уникален без учёта регистра. Для существующего аккаунта повторная регистрация возвращает конфликт, включая заблокированные и удалённые аккаунты; их пароль и состояние не меняются.
- Подтверждение и замена заявки сериализуются по email транзакционной advisory-блокировкой PostgreSQL. После блокировки токен проверяется повторно, чтобы заменённая заявка не создала аккаунт. Если подтверждение завершилось первым, новая регистрация уже получает конфликт существующего аккаунта.

Mail отправляет письмо синхронно. Успешный ответ означает принятие SMTP-сервером, но не гарантирует доставку. При сбое ожидающая заявка может остаться; повторная регистрация с выбранным паролем заменяет её. При сетевом обрыве принятое письмо может дойти даже после ошибки API.

User проверяет активные правила `users.trusted_email_domain` перед сохранением заявки и при подтверждении. `hse.ru` разрешает точный домен, `*.hse.ru` — поддомены, но не корень. Для остальных доменов API возвращает `403`; пустой список запрещает регистрацию.

## PostgreSQL и миграции

Миграции применяет отдельная джоба [Migrator](../migrator/README.md). Начальная миграция `00001_create_accounts.sql` сразу создаёт схему с заявками на регистрацию, обязательным уникальным email аккаунта и связями подтверждения. Она предназначена для пустой БД. Перед запуском обновлённого приложения старую учебную БД нужно пересоздать вместе с историей Goose. Откат удаляет таблицы и типы с данными.

## Локальный запуск

Для запуска всех сервисов выполните `docker compose up --build`. Gateway доступен по адресу `http://localhost:8080`, а письма с подтверждением — в Mailpit по адресу `http://localhost:8025`.

Для локальной проверки с доменами HSE после запуска мигратора однократно выполните:

```sh
docker compose exec -T postgres sh -c 'psql -v ON_ERROR_STOP=1 -U "$POSTGRES_USER" -d "$POSTGRES_DB"' < scripts/db/seed_local_hse_domains.sql
```

Скрипт идемпотентен и не меняет существующие правила. В рабочей БД разрешённые домены добавляются отдельно по решению администратора; это не часть миграций схемы.

Для прямого запуска Go-сервисов поднимите зависимости и Mailpit через Compose, затем запустите Auth, Mail, User и Gateway с их файлами `config.example.yaml`. Необходимые секреты: `POSTGRES_PASSWORD`, `REDIS_PASSWORD` (только Auth), `SMTP_USERNAME` и `SMTP_PASSWORD` (Mail, если SMTP-сервер требует аутентификацию). Для локальной разработки сначала выполните `docker compose up -d postgres redis mailpit`; при прямом запуске Mail направьте его SMTP-настройки на локальный Mailpit (`localhost:1025`, без STARTTLS). Compose привязывает порты сервисов только к localhost. Настройки SMTP Mailpit предназначены только для разработки.

## Внутренний gRPC API

- `Register(email, password)` сохраняет или заменяет заявку, отправляет письмо и возвращает `status: pending`. `user_id` не выдаётся.
- `Login(email, password)` создаёт сеанс только для активного аккаунта с подтверждённой почтой.
- `ConfirmEmail(token)` создаёт аккаунт из актуальной заявки, подтверждает email и удаляет заявку в одной транзакции.
- `GetEmailStatus(user_id)` возвращает состояние email существующего аккаунта. Заявки через этот метод не доступны.

Проверка: `go test ./internal/user/...`. Интеграционные тесты: `go test -tags=integration ./internal/user/repository ./internal/migrator/migrations`.
