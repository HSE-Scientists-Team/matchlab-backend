# Сервис User

User владеет учётными записями, логинами, хешами паролей и принадлежностью адресов электронной почты в схеме PostgreSQL `users`. При регистрации адрес электронной почты не обязателен. Логин при регистрации и входе приводится к нижнему регистру, а сравнение не зависит от регистра. Пароли хранятся как хеши bcrypt. После успешного входа User запрашивает у Auth создание сеанса по gRPC.

## Модель электронной почты

- `user_account.login` уникален без учёта регистра и содержит от 1 до 32 символов ASCII: буквы, цифры, `_`, `-` или `.`. Адрес электронной почты не используется для входа.
- `email_verification_request` хранит один текущий ожидающий подтверждения адрес пользователя и SHA-256-хеш одноразового токена со сроком действия 30 минут. Несколько пользователей могут одновременно запросить один адрес.
- `user_email` хранит только подтверждённые адреса. Уникальный индекс без учёта регистра позволяет закрепить адрес только за одним пользователем. У пользователя может быть один подтверждённый адрес; подтверждение нового адреса заменяет прежний.
- Токен принадлежит пользователю, запросившему подтверждение. Подтверждение токена одного пользователя не подтверждает запрос другого, даже если они указали один адрес. Если другой пользователь подтвердил адрес первым, более поздняя попытка завершается конфликтом, а владелец адреса не меняется.

User передаёт запросы на отправку подтверждений внутреннему gRPC-сервису Mail. Mail отправляет письмо синхронно и возвращает ответ после его принятия SMTP-сервером; при ошибке запрос на отправку завершается ошибкой. Токены подтверждения принадлежат User; Mail не может подтвердить адрес. Поведение доставки описано в [документации Mail](../mail/README.md).

User сохраняет ожидающий токен до вызова Mail. Если SMTP не подтвердит приём, API вернёт ошибку, но запись ожидающего запроса может остаться; повторный запрос заменит её новым токеном. При сетевом обрыве уже принятое письмо может дойти до пользователя, хотя API вернул ошибку.

Подтверждение почты доступно только для активных правил в `users.trusted_email_domain`. Проверка выполняется User перед сохранением запроса и повторяется при подтверждении токена; Mail лишь доставляет письмо и не обращается к БД. `hse.ru` разрешает точный домен, `*.hse.ru` — любой его поддомен, но не корень. Для остальных доменов API возвращает `403` с сообщением «подтверждение почты для этой организации недоступно»; письмо не отправляется. Пустой список правил запрещает подтверждение всех адресов.

## PostgreSQL и миграции

Миграции Goose применяет отдельная джоба [Migrator](../migrator/README.md). В локальном Compose User запускается после её успешного завершения. Текущая миграция `00001_create_accounts.sql` создаёт схему `users`, учётные записи, подтверждённые адреса, запросы на подтверждение и доверенные домены. Её откат удаляет эти таблицы и типы вместе с данными; проверяйте последствия перед откатом.

## Локальный запуск

Для запуска всех сервисов выполните `docker compose up --build`. Gateway доступен по адресу `http://localhost:8080`, а письма с подтверждением — в Mailpit по адресу `http://localhost:8025`.

Для локальной проверки с доменами HSE после запуска мигратора однократно выполните:

```sh
docker compose exec -T postgres sh -c 'psql -v ON_ERROR_STOP=1 -U "$POSTGRES_USER" -d "$POSTGRES_DB"' < scripts/db/seed_local_hse_domains.sql
```

Скрипт идемпотентен и не меняет существующие правила. В рабочей БД разрешённые домены добавляются отдельно по решению администратора; это не часть миграций схемы.

Для прямого запуска Go-сервисов поднимите зависимости и Mailpit через Compose, затем запустите Auth, Mail, User и Gateway с их файлами `config.example.yaml`. Необходимые секреты: `POSTGRES_PASSWORD`, `REDIS_PASSWORD` (только Auth), `SMTP_USERNAME` и `SMTP_PASSWORD` (Mail, если SMTP-сервер требует аутентификацию). Для локальной разработки сначала выполните `docker compose up -d postgres redis mailpit`; при прямом запуске Mail направьте его SMTP-настройки на локальный Mailpit (`localhost:1025`, без STARTTLS). Compose привязывает порты сервисов только к localhost. Настройки SMTP Mailpit предназначены только для разработки.

## Внутренний gRPC API

- `Register(login, password)` создаёт активную учётную запись без адреса электронной почты.
- `Login(login, password)` проверяет учётные данные и возвращает сеанс.
- `RequestEmailVerification(user_id, email)` заменяет ожидающий запрос пользователя и отправляет письмо для подтверждения.
- `ConfirmEmail(token)` подтверждает и закрепляет адрес, если он ещё не принадлежит другому пользователю.
- `GetEmailStatus(user_id)` возвращает `not_set`, `pending` или `verified`, а также текущий и ожидающий подтверждения адреса.

Проверка: `go test ./internal/user/...`. Интеграционный тест Goose использует настоящий PostgreSQL и проверяет правило «несколько ожидающих запросов, один подтверждённый владелец»: `go test -tags=integration ./internal/migrator/migrations`.
