# KAN-38: профиль пользователя

User хранит профиль, достижения, приватность, блокировки и отзывы. Публичный HTTP API обслуживает Gateway, gRPC-контракт — `api/proto/user/v1/profile.proto`. Изменения выполняются для пользователя из Bearer-сеанса, проверенного самим User через Auth; клиент не передаёт автора. Неактивный аккаунт или неподтверждённая почта запрещают операции. Чтение чужого профиля, достижений и отзывов доступно гостю; переданный сеанс обязан быть действительным.

## Профиль и приватность

`PUT /api/v1/users/me/profile` полностью заменяет данные профиля: display_name, avatar_file_id, university, study_level, study_year, specialization, about, open_to_collaboration, project_types (scientific/practical), interests, skills, contact_email и telegram. Имя обязательно; навыки/интересы — до 30 уникальных без учёта регистра тегов, до 80 символов каждый. Описание — до 10000 символов. Аватар должен быть своим, готовым, публичным PNG/JPEG в Media.

`verified` — вычисляемый признак подтверждённой почты с точным доменом hse.ru или edu.hse.ru. Клиент изменить его не может; он не означает подтверждения достижений. Для новых и существующих аккаунтов профиль создаётся миграцией/триггером. Пустой профиль допустим до заполнения.

`GET/PUT /api/v1/users/me/settings` управляет show_contacts и show_participating_projects; по умолчанию false. Контакты видит владелец, текущая команда из доверенного проектного контекста или любой посетитель при show_contacts=true. Блокировка скрывает контакты другой стороне даже при публичности. После завершения проекта доступ команды к скрытым контактам прекращается. show_participating_projects сохраняется как правило для будущего сервиса Projects; список проектов в этой задаче не публикуется.

`GET /api/v1/users/{user_id}/profile` возвращает профиль, среднюю оценку и число отзывов. Контакты фильтруются в User, а не на фронтенде. Не возвращается email для входа: пользователь отдельно задаёт контактный адрес.

## Достижения

`GET/POST /api/v1/users/me/achievements`, `GET/PUT/DELETE /api/v1/users/me/achievements/{id}`, `POST /api/v1/users/me/achievements/{id}/submit`. Чужие достижения: `GET /api/v1/users/{user_id}/achievements`. Списки поддерживают limit 1–100 (по умолчанию 20), offset 0–10000 и фильтр kind.

Виды: education, certificate, scientific, project. Обязательны title; description для scientific/project и institution для education/certificate. Ссылка — только HTTP/HTTPS. Подтверждающий файл — свой готовый приватный файл Media; подписанный URL в БД не сохраняется. Файл не удаляется автоматически вместе с достижением. Владелец видит evidence_file_id и moderation_comment, остальные — только публичные данные и статус.

Новая работа имеет unverified и остаётся видимой. Отправка с URL или доказательством переводит её в pending_review; User не проверяет содержимое внешней ссылки автоматически. Модератор принимает (verified) либо возвращает на исправление (needs_evidence, причина обязательна). Редактирование любых данных сбрасывает статус в unverified. Для PUT обязателен expected_revision из ответа; устаревшая версия возвращает 409. Отправка на проверку также увеличивает revision. Повтор решения или решение после редактирования отклоняются. Удаление логическое и сохраняет историю решений, включая снимок проверенных данных и идентификатор доказательства.

## Внутренние RPC

Gateway не публикует ListVerificationQueue, ReviewAchievement, GetAchievementEvidence, RecordProjectContext и CheckInteraction. Первые четыре требуют Bearer-сеанса активного moderator/administrator. User проверяет роль в PostgreSQL; передача reviewer_user_id или actor_user_id от клиента не используется. Проверять своё достижение нельзя даже модератору. GetAchievementEvidence выдаёт временную ссылку Media, используя владельца из сохранённого достижения. API будущего администратора делегирует его сеанс в gRPC metadata authorization.

Это модель авторизации администраторского пользователя, не идентификация сервисов. Перед автоматической отправкой проектных контекстов из будущего Projects потребуется добавить аутентификацию и отдельные права этого сервиса; принимать такие контексты от обычного пользовательского сеанса нельзя. Auth и другие внутренние RPC должны оставаться в закрытой сети.

## Минимальные данные проектов и отзывы

RecordProjectContext хранит только project_id, title, initiator_user_id, participant_user_ids (включая инициатора) и completed_at_unix. Ноль означает текущую команду; положительное значение — завершённый проект. Статусы публикации, роли, поиск, отклики и публичный CRUD проектов здесь отсутствуют. Контекст записывается транзакционно и сериализуется по project_id. Завершённые контексты неизменяемы; повтор того же снимка идемпотентен, противоречивый снимок запрещён.

`POST /api/v1/users/me/reviews` принимает project_id, target_user_id, title, text, rating (1–5). Автор и адресат должны входить в сохранённый завершённый проект; отзыв о себе запрещён. На пару автор/адресат в проекте допускается один отзыв. Список `GET /api/v1/users/{user_id}/reviews` и собственный `/me/reviews` содержит роль автора, название и дату завершения проекта, полный текст, дату и оценку. Средняя оценка вычисляется из сохранённых отзывов. Создание отзывов возможно после получения доверенного контекста проекта; сейчас публичных средств создавать такой контекст нет.

## Блокировки

`GET /api/v1/users/me/blocks`, `PUT/DELETE /api/v1/users/me/blocks/{id}`. Создание/удаление блокировки идемпотентно, блокировать себя нельзя. CheckInteraction проверяет наличие блокировки в любую сторону, требует сеанс одного из двух пользователей. Будущие сервисы сообщений и приглашений обязаны вызывать эту проверку; текущие команды и отзывы блокировка не удаляет.

## Конфигурация, миграции и проверка

User дополнительно получает media.host/media.port из YAML; Compose использует media:8085, прямой запуск localhost:8085. Секреты по-прежнему через окружение. Миграция 00005 добавляет профиль и достижения, проектные контексты и отзывы, а также точные домены hse.ru и edu.hse.ru. Она сохраняет существующие правила (включая отключённые); Down удаляет новые данные, но не отзывает доменные правила. Миграции 00001–00004 не изменяются. Для выпуска нужны обновлённая конфигурация User и сборка all: старые образы не знают новую историю миграций.

Проверки: `go test ./...`; `go test -tags=integration ./internal/user/profile ./internal/user/repository ./pkg/migrations`. Интеграционный тест проверяет приватность, права, конкурентные решения, сброс проверки, аудит, отзывы, текущие команды и блокировки. Числа int64 в новых HTTP-ответах представлены десятичными строками по protobuf JSON (created_at_unix и др.).

Пример:

```sh
curl -X PUT https://api.matchlab.space/api/v1/users/me/profile \
  -H "Authorization: Bearer $ACCESS_TOKEN" -H 'Content-Type: application/json' \
  -d '{"display_name":"Анна","about":"Исследую компьютерное зрение","skills":["Python"],"project_types":["scientific"],"open_to_collaboration":true}'
```
