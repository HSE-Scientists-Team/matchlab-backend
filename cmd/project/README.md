# Project — KAN-39

Project владеет схемой `projects`: проектами, ролями, составом команды, откликами, приглашениями, аудитом модерации и transactional outbox. Межсервисных FK к User нет. User — владелец личности, профиля, блокировок и отзывов. Project обращается к нему только через gRPC.

## Жизненный цикл и права

Новый проект сразу публикуется (`recruiting`). Обязательны название (до 255 символов), тип scientific/practical, сфера (до 120), проблема и цель (до 10000 каждая), даты и 1–30 ролей. Даты принимаются как YYYY-MM-DD либо YYYY-MM; месяцы преобразуются в начало первого и конец последнего месяца. Теги/навыки — до 30 уникальных строк по 80 символов. У роли 1–100 мест, описание до 10000 символов.

Владелец определяется из Bearer-сеанса через User.GetIdentity, а не из JSON. Переходы:

- publish: unpublished → recruiting;
- unpublish: recruiting → unpublished, текущие заявки сохраняются, новые не принимаются;
- start: recruiting → active, набор закрывается, ожидающие заявки отменяются;
- complete: active → completed, фиксируется команда для отзывов;
- cancel: recruiting/unpublished/active → cancelled, без права на отзывы.

Изменения описания, ролей, жизненного цикла и модерации требуют expected_revision. Истёкшая версия даёт 409. Завершённый/отменённый проект владелец не изменяет. У активного проекта можно редактировать описание, но не роли. Скрытие модератором независимо от жизненного цикла: владелец не может сам снять этот флаг. Скрытый или снятый с публикации проект видят только владелец и текущая команда. Публичная карточка не раскрывает участников и счётчик заявок; команда доступна её участникам, счётчик — инициатору. Участие в профиле ограничивается настройкой User; скрытое участие видит сам пользователь и инициаторы соответствующих проектов.

## Роли и набор

Create принимает начальные роли в одной транзакции с проектом. Последующие изменения ролей выполняются отдельными SaveRole/DeleteRole, а Update заменяет описание и не принимает список roles. Сократить число мест ниже занятого нельзя. Свободная роль удаляется логически, её ожидающие заявки отменяются, история сохраняется. Последнюю роль удалить нельзя.

Пользователь откликается сам; инициатор приглашает кандидата на конкретную роль. Принять/отклонить application может инициатор, invitation — приглашённый. Отозвать application может автор, invitation — инициатор. На роль и кандидата допускается одна ожидающая заявка. После отклонения или отзыва можно подать новую. Принятие любой заявки отменяет остальные ожидающие заявки этого кандидата в проекте.

Изменения сериализуются блокировкой строки проекта, поэтому параллельные решения не переполняют роль и не добавляют одного человека дважды. Перед приглашением и принятием проверяется блокировка в User. Проверка блокировки и изменение Project не являются распределённой транзакцией; блокировка, появившаяся после проверки, не исключает человека из уже принятой команды. Инициатор не может исключить себя; участник может выйти, пока проект не завершён/отменён. Эти действия освобождают место, но не стирают историю.

## Профили, приватность и отзывы

Каждая мутация сохраняет текущий состав и статус в `projects.context_outbox` в той же SQL-транзакции. Worker повторяет доставку в User.RecordProjectContext с отдельным `PROJECT_SYNC_TOKEN` (не менее 32 байт). User проверяет сервисный credential, а не роль пользователя, и применяет только новые source_revision. Повтор/запоздалое событие безопасны; завершённый снимок неизменяем. Односторонняя зависимость Project → User не создаёт обратного RPC-вызова.

В User хранится только проекция: текущая команда для контактов, отмена для прекращения доступа и завершённый состав для отзывов. После завершения допускается задержка до доставки outbox, обычно около двух секунд: отзыв нельзя создать раньше подтверждённого снимка. При недоступном User события остаются в БД. Удаление/отмена состава не выдаёт права на отзывы. Общий токен передаётся через окружение только User и Project; не помещайте его в YAML/Git/логи. Без него User запрещает синхронизацию, Project не запускается.

## HTTP и внутренний API

Gateway предоставляет `/api/v1/projects`, карточку `/{id}`, `/transitions`, `/roles`, `/applications`, `/invitations`, `/joins`, `/members/{user_id}`, `/membership` и `/api/v1/project-joins`. Поиск, мои проекты и фильтры описаны в OpenAPI. Просмотр каталога доступен гостю; переданный credential обязан быть действительным. Изменения требуют активного аккаунта с подтверждённой почтой. Контакты инициатора/участников клиент получает из ProfileService с его правилами приватности; Project не копирует профили.

Внутренние gRPC Moderate, ListModeration и ModerationHistory доступны только moderator/administrator через User.GetIdentity и не имеют маршрутов в Gateway. Скрытие/восстановление требует причины и версии, решения сохраняются в аудите. Жалобы на проект принимает существующий Support. Кнопки чата пока используют идентификаторы пользователей: чат и доставка push-уведомлений — отдельные сервисы, здесь они не имитируются.

## Запуск и выпуск

Локально: `docker compose up --build`. Compose передаёт одинаковый тестовый PROJECT_SYNC_TOKEN в User и Project; это credential только локального окружения. Прямой запуск: задайте POSTGRES_PASSWORD и PROJECT_SYNC_TOKEN, запустите User и `go run ./cmd/project -config cmd/project/config.example.yaml`.

Порт внутреннего gRPC — 8087. Config YAML содержит grpc, peers.user и postgres. При старте применяется весь общий SQL-набор, миграция 00006 создаёт таблицы Project и версии проекции User. Down удаляет все проекты, заявки, историю и outbox, отзывает их незавершённые проекции команды и сохраняет завершённые снимки для истории отзывов. Опубликованные SQL 00001–00005 не изменяются.

Для k3s нужны отдельный Deployment/Service Project, конфигурации Search и Recommendation, адреса новых сервисов в Gateway и общий защищённый PROJECT_SYNC_TOKEN в User/Project. Сборка all включает три новых образа; propose_deploy добавляет их digest в ConfigMap инфры. Сами Deployment принадлежат matchlab-infra; добавление digest не создаёт их автоматически. Старые образы не знают миграцию 00006: выпускать нужно весь набор сервисов.

Проверки: `go test ./...`, `go test -tags=integration ./internal/project ./internal/user/profile ./pkg/migrations`. Проверяются конкурентное принятие на последнее место, права, блокировки, жизненный цикл, приватность каталога, модерация, сохранность и повторная доставка outbox.

С KAN-35 модерация, административный просмотр, история с пагинацией и статистика требуют Ed25519 assertion Admin с audience=project (ADMIN_PUBLIC_KEY). Новые акторы пишутся в actor_admin_id; actor_user_id сохраняется для старой истории. Публичный пользовательский Bearer и роль профиля эти права не дают. HTTP-фасад: /api/v1/admin/projects.
