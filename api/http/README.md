# HTTP API Gateway

## Рекомендации: batch и cold start

`GET /api/v1/recommendations/people?limit=20` и `/api/v1/recommendations/projects?limit=20` требуют Bearer-сеанс с подтверждённой почтой. limit 1–100, offset не поддерживается. Сохраняются `items` и строковое `total`; только эти маршруты дополнительно возвращают необязательный объект `recommendation`:

```json
{
  "items": [],
  "total": "0",
  "recommendation": {
    "schema_version": 1,
    "run_id": "",
    "model": "fallback-v1",
    "generated_at": "",
    "items": []
  }
}
```

Для каждого выданного ID `recommendation.items` содержит `id`, `score` (0–1, не вероятность), `factors` (например `shared_skills`, `role_skills`, `project_text_similarity`), `role_id`, `fallback` и `model`. Сопоставляйте по ID (`user_id` у карточки человека, `id` у проекта), не по индексу. `generated_at` — время batch-снимка; профильные данные/права проверяются заново при запросе. После изменения профиля факторы/score могут оставаться от предыдущего снимка, но не содержат старых значений полей.

Нет персонального кеша или Redis недоступен — live catalogue fallback, без вымышленных совпадений. Смешанная выдача может содержать batch и fallback элементы. `total` — размер доступного каталога, не число персональных совпадений; фильтрация вместимости/блокировок может сократить список проектов. Ошибка владельца данных не разрешает выдавать устаревшие карточки. Обычные Search/List ответы объект `recommendation` не добавляют. Старые внутренние серверы без provenance по-прежнему совместимы.

[`openapi.yaml`](openapi.yaml) описывает реализованные маршруты, JSON-запросы и ответы, ошибки и Bearer-авторизацию. Scalar показывает эту спецификацию по адресу `http://localhost:8084`; локальный Gateway доступен на `http://localhost:8080`. Запуск окружения описан в [README репозитория](../../README.md).

В Scalar все файловые операции находятся в группе «Файлы»: сначала цельная загрузка и общие операции, затем multipart. После обновления спецификации пересоберите сервис `api-docs` и обновите страницу через Ctrl+F5. После изменения кода API требуется пересборка Gateway и Media. Спецификация работающего Scalar доступна по адресу `http://localhost:8084/openapi.yaml`.

Scalar обслуживает браузерный бандл локально, без загрузки с CDN при открытии страницы. Gateway разрешает браузерные запросы с адресов, указанных в его CORS-конфигурации; для локального Scalar это `http://localhost:8084` и `http://127.0.0.1:8084`.

## Авторизация

Для локальной регистрации сначала должны быть добавлены разрешённые домены из [инструкции User](../../cmd/user/README.md). В `POST /api/v1/auth/register` укажите `email` и `password`. Ответ `201` содержит `status: pending`, без сеанса и `user_id`. Письмо доступно в Mailpit по адресу `http://localhost:8025`.

Токен из ссылки в письме передайте в JSON-поле `token` метода `POST /api/v1/auth/email/confirm`. Затем войдите через `POST /api/v1/auth/login` с `email` и `password`. Полученный `access_token` указывайте в заголовке `Authorization: Bearer <access_token>` или в поле Bearer Auth в Scalar. До подтверждения регистрации вход возвращает `401`. Повторная регистрация с тем же email обновляет заявку и аннулирует старую ссылку.

Создание, подтверждение, удаление и все multipart-операции требуют действительного сеанса и подтверждённой почты. Gateway определяет владельца из сеанса: `user_id` в HTTP-запросе указывать не нужно.

Метаданные и ссылка на скачивание публичного файла (`is_public: true`) доступны без Authorization. Приватный файл доступен владельцу. Если Authorization передан, он должен быть действительным, а почта — подтверждённой. Чужой приватный файл и чужая загрузка возвращают `404`, включая попытку изменить публичный файл другим пользователем.

Bearer-токен передаётся только Gateway. Запросы по подписанным URL идут напрямую в S3 с выданными заголовками; Gateway не принимает и не проксирует байты файлов.

## Файловые операции

Во всех маршрутах `{id}` — значение `file.id`, полученное при создании загрузки.

| Метод и маршрут | Что указать | Успешный ответ |
| --- | --- | --- |
| `POST /api/v1/media/files` | Bearer, JSON с описанием файла | `201`: `file`, `upload_url`, `method`, `headers`, `expires_at_unix` |
| `POST /api/v1/media/files/{id}/complete` | Bearer владельца, ID файла; тело не требуется | `200`: `file` со статусом `ready` |
| `GET /api/v1/media/files/{id}` | ID файла; Bearer для приватного файла | `200`: метаданные в объекте `file` |
| `GET /api/v1/media/files/{id}/download-url` | ID готового файла; Bearer для приватного файла | `200`: `download_url`, `expires_at_unix` |
| `DELETE /api/v1/media/files/{id}` | Bearer владельца, ID готового файла; тело не требуется | `204`: объект удалён, файл помечен `deleted` |
| `POST /api/v1/media/files/multipart` | Bearer, JSON с описанием файла | `201`: `file` и состояние multipart-сессии |
| `GET /api/v1/media/files/{id}/multipart` | Bearer владельца, ID файла | `200`: состояние сессии и принятые части |
| `DELETE /api/v1/media/files/{id}/multipart` | Bearer владельца, ID файла; тело не требуется | `204`: загрузка отменена |
| `POST /api/v1/media/files/{id}/multipart/part-urls` | Bearer владельца, JSON с `part_numbers` | `200`: массив `parts` со ссылками |
| `POST /api/v1/media/files/{id}/multipart/complete` | Bearer владельца, JSON с номерами и ETag всех частей | `200`: `file` со статусом `ready` |

Для JSON-запросов нужен `Content-Type: application/json`. Ответы Gateway не кешируются (`Cache-Control: no-store`). Изменение публичности и список файлов пока не реализованы.

## Описание файла и ограничения

Для обычной и multipart-загрузки используются одинаковые поля:

| Поле | Что указать |
| --- | --- |
| `original_name` | Имя файла без пути, от 1 до 255 символов, без управляющих символов |
| `content_type` | Разрешённый MIME-тип: локально `application/pdf`, `image/jpeg` или `image/png` |
| `size_bytes` | Точный размер всего исходного файла в байтах, положительное число |
| `is_public` | `true` для публичного чтения, `false` для приватного; по умолчанию `false` |

Пример JSON:

```json
{
  "original_name": "report.pdf",
  "content_type": "application/pdf",
  "size_bytes": 9437184,
  "is_public": false
}
```

Локальный лимит всего файла — **100 МиБ (104857600 байт)**, для обоих способов загрузки. Media проверяет разрешённый MIME-тип, метаданные Content-Type в S3 и размер. Для новых загрузок ожидаемый размер сохраняется в БД; у старых обычных файлов он может быть неизвестен, тогда проверяются положительный размер и общий лимит.

Содержимое PDF или изображения не разбирается: произвольные байты с подходящими размером и метаданными могут пройти проверку. Расширение имени само по себе не подтверждает формат.

## Цельная загрузка

1. Отправьте описание файла в `POST /api/v1/media/files` и сохраните `file.id`.
2. Выполните запрос на полученный `upload_url` методом из `method` (PUT). В теле передайте байты всего файла, в заголовках — значения из `headers`. Размер и Content-Type должны совпадать с описанием файла. `Content-Length` клиент может сформировать автоматически из тела. Заголовок `If-None-Match: *` запрещает перезапись существующего объекта.
3. Вызовите `POST /api/v1/media/files/{id}/complete` с Bearer-токеном владельца, без тела. Media проверит объект через HEAD и сохранит `ready`. Успех — `200` с объектом `file`; повтор возвращает сохранённые метаданные.

PUT-ссылка локально действует **10 минут**. Открытие этой ссылки в браузере не загружает файл: нужен PUT с байтами. Не используйте `multipart/form-data`. Подписанный URL передавайте без изменения адреса и параметров. Если JSON экранирует `&` как `\u0026`, сначала разберите JSON, чтобы получить обычную строку URL.

## Скачивание файла частями и докачка

Получите `download_url` через `GET /api/v1/media/files/{id}/download-url`, затем выполняйте GET напрямую в S3. Локальный срок ссылки — **5 минут**; она даёт доступ любому её получателю до истечения срока. При истечении запросите новую для того же файла.

Для фрагмента укажите заголовок `Range: bytes=начало-конец`. Границы включительные, отсчёт начинается с нуля. Например, первый МиБ запрашивается как `Range: bytes=0-1048575`. Одна подписанная ссылка подходит для разных диапазонов; отдельный маршрут Gateway для частей не нужен.

Для файла больше 1 МиБ ответ на такой запрос должен содержать:

```http
HTTP/1.1 206 Partial Content
Content-Range: bytes 0-1048575/<полный размер файла>
Content-Length: 1048576
```

Проверьте код `206`, границы `Content-Range` и длину полученных байтов. Если сервер вернул `200` с полным файлом, не считайте ответ запрошенным фрагментом. Диапазон с началом за пределами файла возвращает `416`.

Для докачки после сохранённых 1048576 байт укажите `Range: bytes=1048576-` и допишите полученные байты к тому же файлу. При обрыве продолжайте с фактического количества уже сохранённых байтов. Сохраняйте и проверяйте ETag объекта, чтобы не объединить разные версии файла; итог можно проверить сравнением SHA-256 с исходным файлом.

Диапазон выбирает клиент: скачивание может быть последовательным или параллельным. Первая половина байтов JPEG/PNG не означает верхнюю половину изображения, поскольку байты представляют сжатый формат.

Для браузера S3 CORS должен разрешать заголовок `Range` и открывать чтение `Content-Range`, `Accept-Ranges`, `ETag`. Интеграционные проверки описаны в [README Media](../../cmd/media/README.md#проверка).

## Загрузка файла частями с докачкой

### Создание сессии

В `POST /api/v1/media/files/multipart` передайте Bearer-токен и описание всего файла: `original_name`, `content_type`, `size_bytes`, `is_public`.

Сохраните `file.id`. Ответ содержит `status`, `part_size_bytes`, `part_count`, `expected_size_bytes`, `expires_at_unix`, `uploaded_bytes`, `parts`. Номера частей начинаются с 1. Локально размер части — **8 МиБ**, срок сессии — **24 часа с момента создания**. Последняя часть может быть меньше остальных.

### Получение ссылок и отправка частей

В `POST /api/v1/media/files/{id}/multipart/part-urls` укажите Bearer-токен владельца и JSON:

```json
{"part_numbers": [1, 2]}
```

За один запрос допускается от 1 до 100 уникальных номеров в пределах `part_count`. Ответ `parts` содержит для каждой части `part_number`, `size_bytes`, `upload_url`, `method`, `headers`, `expires_at_unix`. Этот маршрут только выдаёт ссылки; он не принимает байты части.

Для части с номером `N` возьмите байты исходного файла со смещения `(N - 1) * part_size_bytes`, длина — выданный `size_bytes`. Отправьте их методом PUT на `upload_url`, передав заголовки из `headers`, без Bearer-токена Gateway. Не используйте `multipart/form-data`. В браузере `Content-Length` формируется автоматически из тела.

Части можно отправлять независимо. Ссылка действует **10 минут с момента выдачи**, но не дольше оставшегося срока сессии. При истечении запросите новую для того же номера: уже принятые части сохраняются. Повторный PUT того же номера заменяет часть, поэтому сохраните новый ETag.

### ETag и завершение

После каждого успешного PUT сохраните заголовок `ETag` из ответа S3 вместе с номером части. ETag идентифицирует версию загруженной части; он нужен S3 для сборки, а не для проверки SHA-256. Одного номера недостаточно, поскольку часть могла быть заменена.

В `POST /api/v1/media/files/{id}/multipart/complete` передайте Bearer-токен владельца и полный список номеров частей с сохранёнными ETag:

```json
{
  "parts": [
    {"part_number": 1, "etag": "\"ETAG_FROM_FIRST_PUT\""},
    {"part_number": 2, "etag": "\"ETAG_FROM_SECOND_PUT\""}
  ]
}
```

Список должен содержать все номера ровно один раз; порядок произвольный. Размеры частей в запросе завершения не нужны. ETag передавайте в виде строки, как вернул S3, включая кавычки, если они есть; JSON-сериализатор экранирует их автоматически.

Media проверяет фактические части, размеры и ETag, сохраняет список в БД и переводит сессию в `completing`. Затем собирает объект в S3, проверяет итоговый размер и Content-Type и сохраняет `ready` для файла, `completed` для сессии. Успех — `200` с объектом `file`. После этого можно получить `download_url` обычным способом.

При потере ответа повторите завершение с тем же списком. Если S3 отверг устаревший ETag, клиент получает `409`, а сессия возвращается в `uploading`: повторите нужную часть и завершение с её новым ETag. Для multipart используйте `/multipart/complete`; обычная `/complete` не подтверждает такую загрузку.

### Прогресс и возобновление

В `GET /api/v1/media/files/{id}/multipart` укажите Bearer-токен владельца, даже для публичного файла. Ответ содержит принятые части и `uploaded_bytes`; процент рассчитывается как `100 * uploaded_bytes / expected_size_bytes`.

Это прогресс полностью принятых частей. Байты текущего PUT учитывайте на клиенте. После обрыва используйте тот же ID сессии и тот же исходный файл. Сверьте номера и сохранённые ETag с состоянием; для отсутствующей или сомнительной части получите новую ссылку и повторите PUT.

SeaweedFS 4.47 может перечислить несколько ETag одного номера после повторной отправки. Прогресс учитывает номер один раз, а завершение проверяет именно ETag, переданный клиентом. Сохраняйте ETag последнего успешного PUT выбранной части.

### Отмена сессии

Сначала остановите текущие PUT, затем вызовите `DELETE /api/v1/media/files/{id}/multipart` с Bearer-токеном владельца, без тела.

Media вызывает AbortMultipartUpload в S3, затем сохраняет `aborted` для сессии и `failed` для файла. Строки БД физически не удаляются. Успех и повтор отмены — `204`; `completing` и `completed` возвращают `409`.

Просроченная сессия не выдаёт новые ссылки и не принимает новое клиентское завершение. Фоновая задача пробует завершить её по данным S3 либо очищает незавершённую загрузку. Состояния сессии: `uploading`, `completing`, `completed`, `aborted`.

## Удаление готового файла

В `DELETE /api/v1/media/files/{id}` укажите Bearer-токен владельца и ID готового файла, без тела. Это общий маршрут для обычной и multipart-загрузки.

Media сохраняет намерение `deleting`, удаляет объект из S3, затем сохраняет `deleted` и дату удаления. Успех и повтор владельцем — `204`; чужой файл, включая публичный, — `404`; отсутствие сеанса — `401`; `pending` и `failed` — `409`.

Файл в `deleting` или `deleted` скрыт из чтения. При сбое удаление повторяет фоновая задача. Запись БД остаётся. Удаление объекта не отзывает ранее выданные PUT-ссылки; в bucket с versioning старые версии очищаются отдельной политикой хранилища.

## Фоновая проверка

Media выполняет задачу при старте и затем каждые **10 минут** по локальной конфигурации. Все `pending`, у которых `updated_at` в БД старше **24 часов**, обрабатываются пакетами по 100:

- Корректный готовый объект подтверждается; полный однозначный multipart собирается и становится `ready` / `completed`.
- Отсутствующая, неполная или некорректная по размеру/типу загрузка очищается в S3; только после успешной очистки сохраняются `failed` / `aborted`.
- Временная ошибка S3 или БД оставляет состояние для следующего запуска.

Задача также восстанавливает `completing`, обрабатывает просроченные multipart-сессии и повторяет удаления `deleting`. Прямые PUT в S3 не меняют `media.file.updated_at`. При нескольких разных ETag одного номера без сохранённого клиентского списка автоматическая сборка неоднозначна, и загрузка отменяется.

## Ошибки и локальная проверка

| Код | Причина |
| --- | --- |
| `400` | Некорректный JSON или параметры |
| `401` | Отсутствующий или недействительный сеанс |
| `403` | Неподтверждённая почта или запрет доступа |
| `404` | Отсутствующий или недоступный файл/сессия |
| `409` | Неподходящее состояние, неполные части, неверные ETag или метаданные объекта |
| `500` | Внутренняя ошибка |
| `503` | Недоступная зависимость |
| `504` | Тайм-аут Media |

Ошибки файловых обработчиков Gateway возвращаются в JSON-поле `error`. Текстовое `404 page not found` может означать неверный адрес или старый образ Gateway. Запросы API направляйте на порт 8080, интерфейс Scalar открыт на 8084, байты файла передавайте по выданному S3 URL.

Для старой локальной БД сверяйте схему и историю по [README миграций](../../pkg/migrations/README.md). Уже применённая миграция не выполняется повторно после изменения её SQL. В локальном S3 CORS разрешены PUT и чтение ETag; рабочее окружение настраивается отдельно.

## Создание жалобы

Фронт предварительно загружает и подтверждает вложения через Media. Автор берётся из сеанса;
в JSON нужно указать ровно одну цель и 0–20 уникальных ID готовых файлов автора.
Тема — 1–255 символов, описание — 1–10000 после удаления пробелов по краям.
Цели проверяются по UUID, существование пользователя/проекта пока не проверяется.

```sh
curl -X POST http://localhost:8080/api/v1/complaints \
  -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{"subject":"Жалоба на пользователя","description":"Описание нарушения","target_user_id":"00000000-0000-4000-8000-000000000002","file_ids":[]}'
```

Для жалобы на проект используйте `target_project_id` вместо `target_user_id`.
С вложениями: `file_ids: ["UUID_READY_FILE"]`. Ответ `201 Created`:

```json
{"id":"00000000-0000-4000-8000-000000000004","status":"open","created_at":"2026-10-12T12:00:00Z"}
```

Ошибки: `400` — некорректные поля/цель/дубли файлов, `401` — сеанс, `403` — неподтверждённая почта,
`404` — отсутствующее или чужое вложение, `409` — файл не ready, `500` — ошибка сохранения,
`502` — некорректный ответ Support, `503` — недоступность зависимости/тайм-аут.
Повтор запроса создаёт новую жалобу. Для обновления локальных образов:
`docker compose up -d --build gateway support api-docs`.

Профили KAN-38: `/api/v1/users/me/profile`, настройки, достижения, блокировки и отзывы. Чтение `/api/v1/users/{user_id}/profile`, achievements и reviews допускает гостя; внутренние методы модерации не представлены HTTP-маршрутами. Контракты и примеры — в [документации User](../../cmd/user/PROFILE.md).

## Личные текстовые чаты

Все запросы требуют Bearer-сеанс активного пользователя с подтверждённой почтой.
Собеседник определяется по user_id, отправитель — из сеанса. Пример открытия:

```sh
curl -X POST http://localhost:8080/api/v1/chat/conversations \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"user_id":"00000000-0000-4000-8000-000000000002"}'
```

Ответ 201 (новый) или 200 (существующий) содержит id диалога. Сохраните его в CONVERSATION_ID.
Список: GET `/api/v1/chat/conversations?limit=20&cursor=...`; курсор берётся из next_cursor.

```sh
curl -X POST "http://localhost:8080/api/v1/chat/conversations/$CONVERSATION_ID/messages" \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"client_message_id":"00000000-0000-4000-8000-000000000003","body":"Привет!"}'
```

Фронт генерирует новый client_message_id для каждого нового сообщения. При сетевом сбое повторяет
запрос с прежним ID и тем же текстом: сервер вернёт сохранённое сообщение (200 вместо 201).
Другой текст с прежним ID — 409. Разрешён обычный текст длиной 1–10000 символов, не только пробелы;
HTML отображается как текст. Вложений, редактирования и удаления нет.

История: GET `/api/v1/chat/conversations/{id}/messages?limit=50`.
Старые сообщения: before_seq=N; новые: after_seq=N (можно 0). Границы исключительные;
оба фильтра одновременно запрещены. Ответ items всегда в порядке seq ASC, has_more сообщает о продолжении.
Для polling передавайте after_seq последнего полученного сообщения и продолжайте, пока has_more=true.

```sh
curl -X PUT "http://localhost:8080/api/v1/chat/conversations/$CONVERSATION_ID/read" \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"last_read_seq":12}'
```

Ответ 204. Отметка только увеличивается и не превышает последний номер. Просмотр истории автоматически
не отмечает сообщения прочитанными. unread_count считает только входящие сообщения.
Все int64 в ответах (номера, счётчики, created_at_unix) — десятичные строки ProtoJSON.
Чужой или отсутствующий диалог — 404. При блокировке в любую сторону новые сообщения запрещены (403),
история доступна участникам. Прочие ошибки описаны в OpenAPI и [README Chat](../../cmd/chat/README.md).

Обновление локальных образов: `docker compose up -d --build chat gateway api-docs`.

## Допустимые строковые значения

Статусы, типы, категории, роли сотрудников и команды переходов описаны в OpenAPI как `enum`. В Scalar откройте схему поля: описание объясняет каждое значение. Общие схемы (например, `ProjectStatus`, `AchievementStatus`, `TicketAction`) используются и публичными, и административными маршрутами.

Фильтры описаны отдельно от ответов: `closed` объединяет закрытые жалобы, но статус самой жалобы — `resolved` или `declined`. Отсутствующий параметр и пустая строка отключают соответствующий фильтр. Изменение статуса пользователя допускает только `active` / `blocked`, хотя ответ может содержать `deleted`.

Названия ролей в проектах, уровень образования, теги и другие свободные поля остаются строками. Модели и факторы рекомендаций зависят от версии расчёта и также не ограничиваются enum.

Каталог значений и пояснений: [`scripts/api/string-enums.json`](../../scripts/api/string-enums.json). После его изменения выполните `go run ./scripts/api/admin-openapi.go --write`; перед push — ту же команду с `--check`. JSON-формат ответов и строковые gRPC-поля не меняются.
