# Миграции при запуске сервисов

Gateway, Auth, User и Mail вызывают `migrations.Apply` до открытия HTTP/gRPC-порта. Каждый образ содержит весь SQL-набор из этого пакета. Отдельного migrator нет. При каждом запуске проверяется история Goose; SQL уже применённых версий не выполняется повторно. PostgreSQL обязателен для старта всех четырёх процессов; после миграций только User держит соединение для работы с учётными записями.

Настройки подключения находятся в `postgres` YAML, пароль — только в `POSTGRES_PASSWORD`. `postgres.migration_timeout` ограничивает подключение, ожидание блокировки и выполнение миграций суммарно; по умолчанию 5 минут. Ошибка, отмена или превышение срока завершает запуск с ненулевым кодом, API ещё не принимает запросы. SIGTERM/SIGINT отменяет ожидание и выполнение.

## Параллельные экземпляры и релизы

Все процессы в одной БД используют один session advisory lock (`836174251409`). Блокировка охватывает подготовку схемы, чтение истории, проверку SQL-отпечатков и весь запуск Goose. После получения lock следующий процесс заново читает БД, поэтому выполненные другим сервисом миграции не повторяются. Блокировка и SQL используют одну физическую сессию PostgreSQL: при её потере транзакция прерывается, а lock освобождается. Это работает и между разными Pod/ВМ, а не только внутри Go-процесса. Используйте прямое PostgreSQL-подключение: PgBouncer в transaction pooling несовместим с session advisory locks.

Отдельный `goose.Provider` на каждый вызов не использует глобальные изменяемые настройки Goose. Все SQL-миграции выполняются в транзакциях; `NO TRANSACTION` отклоняется. В `users.goose_db_version` хранится версия, в `users.migration_checksum` — SHA-256 исходного SQL-файла. Отпечаток записывается в той же транзакции, что DDL и версия Goose. После аварии не останется успешной версии без отпечатка. При транзакционном сбое не фиксируются DDL, версия и отпечаток этой миграции; можно повторить запуск после устранения причины.

Сервис отказывается стартовать, если БД содержит неизвестную ему миграцию или SQL под известным номером отличается. Поэтому новый релиз может поднять версию, но последующий запуск старого релиза не откатывает её и завершится ошибкой. Нумерация должна быть общей и монотонной: согласуйте номера между ветками и не меняйте уже применённые SQL-файлы. При переходе с истории Goose без отпечатков первый запуск фиксирует текущие файлы как baseline: проверить прежнее содержимое SQL задним числом невозможно.

Блокировка гарантирует сериализацию миграций, но не совместимость уже работающего старого кода с будущей схемой. Для rolling release используйте expand/contract: сначала добавляйте совместимые поля/таблицы, затем обновляйте приложение, и лишь после вывода старых экземпляров удаляйте старую схему. Уже работающий старый процесс автоматически не останавливается при новой миграции. Для несовместимых изменений нужен контролируемый останов приложения. Down автоматически не вызывается; откат образов не является откатом данных.

Начальная `00001_create_accounts.sql` рассчитана на пустую учебную БД. Она создаёт схему регистрации через email и подтверждение. Откат SQL удаляет данные таблиц; резервные копии обязательны перед ручными операциями с БД.

Проверка: `go test ./pkg/migrations ./pkg/postgres`; интеграционные тесты PostgreSQL: `go test -tags=integration ./pkg/migrations`. Они проверяют одновременные запуски, ровно одно выполнение, отмену ожидания, разные версии, разные SQL под одним номером и восстановление после SQL-ошибки.
